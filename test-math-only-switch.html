Math Only Switch Test

Test Case: $x$\ny\n$z$

Initial state: Mixed mode (mathOnly: false)

Expected: 3 lines
- Line 1: x (math)
- Line 2: y (text)
- Line 3: z (math)

After switching to Math Only (mathOnly: true)

Expected: 1 line with "xyz" all in math mode
User reports: Visual looks correct (xyz), but bounding box not updated

Key Questions:

  1. When mathOnly switches from false to true, what happens to the delimiters?
  2. What happens to the newlines between math expressions?
  3. Is the text being processed correctly in consumeMathNewlines?
  4. Is redrawTextBoundingBox getting the correct measurements?

Code Analysis:

consumeMathNewlines logic:
- If useTex OR !mathOnly (mixed mode):
  - Replace newlines in math segments with spaces
- If !useTex AND mathOnly (AsciiMath math-only):
  - Keep newlines in math segments

For text "$x$\ny\n$z$":

Mixed mode (mathOnly: false):
- splitMath produces: ["", "$x$", "\n", "y", "\n", "$z$", ""]
- Even indices (0,2,4,6) are text segments
- Odd indices (1,3,5) are math segments
- Since !mathOnly, newlines in math segments (odd) are replaced with spaces
- But indices 1,3,5 are "$x$", "y", "$z$" - no newlines IN the math segments
- So nothing changes, stays as "\n" between segments
- Result: 3 lines preserved

Math-only mode (mathOnly: true):
- The ENTIRE text becomes math: "x\ny\nz" (delimiters removed)
- splitMath probably produces: ["", "x\ny\nz", ""]
- Since mathOnly AND !useTex, newlines are KEPT
- Result: "x\ny\nz" with newlines preserved = 3 lines!

But user says it displays as "xyz" (1 line) - so something else is happening!

Hypothesis:

The visual rendering is correct (shows "xyz" on one line), which means the newlines ARE being removed somewhere. But the bounding box calculation might be using different logic that still thinks there are 3 lines.

OR: The bounding box is being calculated BEFORE the mathOnly switch completes, using the old text structure.
